## 四、两条路线选择

### 路线 A：渐进式改进（推荐用于当前阶段）

在现有代码基础上持续修补，风险可控，不阻断演示。

```
当前状态 → 演示前修复（10-15h）→ 演示 → 短期改进（1-2周）→ 中长期重构（1-2月）
```

**优点**：风险低、可演示、投入产出比高
**缺点**：技术债持续累积，架构问题难以根治

### 路线 B：全量重写（适用于团队充裕时）

按 [PROJECT_REWRITE_PLAN.md](./PROJECT_REWRITE_PLAN.md) 的 6 人四周方案推倒重来。

```
Week 1 地基 → Week 2 核心功能 → Week 3 集成 → Week 4 打磨交付
```

**优点**：架构根治、技术债清零、代码质量飞跃
**缺点**：投入大（6人×4周=120人天）、有延期风险、需并行维护旧系统

### 建议

**当前阶段（演示前）**：走路线 A，只做"演示前必做"的 9 项（约 10-15h）。

**演示后**：根据团队资源和业务需求决定：
- 如果只需局部改进 → 继续路线 A 的短期+中长期项
- 如果要彻底升级 → 走路线 B 全量重写
- 混合方案：核心模块（Agent 系统）重写 + 周边模块渐进改进
