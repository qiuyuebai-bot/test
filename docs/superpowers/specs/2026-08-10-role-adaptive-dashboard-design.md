# 角色自适应 Dashboard 与独立运维入口设计

## 1. 背景与问题

当前 `Dashboard` 面向所有角色执行同一套管理员监控流程：首次进入并发请求系统指标、学习者列表、Agent 状态、资源列表和任务列表；页面同时展示全局统计、Agent 状态、近期任务和学习者概览。30 秒轮询及标签页可见性刷新也没有角色分支。

这造成三类问题：

1. 学习者首屏信息密度过高，无法判断下一步行动。
2. 学习者和教师请求了不需要的系统级数据，浪费带宽并扩大权限暴露面。
3. 运维监控和学习工作流混在同一入口，角色边界不清晰。

已有 `user.role`（`learner`、`teacher`、`admin`）和按角色读取学习者数据的 Store 逻辑；已有 `/ops`、`/multi-agent`、`/metrics`、`/monitoring` 等系统管理入口。本设计复用这些基础能力，不新增认证机制。

## 2. 目标与非目标

### 目标

- 为学习者、教师、管理员提供不同的 Dashboard 信息架构。
- 将系统监控保留在独立运维入口，避免 Dashboard 承担两种产品职责。
- 为新学习者提供明确的“下一步该做什么”行动卡。
- 按角色限制首屏数据请求和刷新策略。
- 让请求数量、轮询行为、引导阶段和权限边界可自动化验证。

### 非目标

- 本次不重做全局导航和视觉设计系统。
- 本次不重构 Agent、资源或报告业务逻辑。
- 本次不以 localStorage 作为唯一的首次登录或引导完成状态来源。

## 3. 角色信息架构

### 学习者：学习工作台

首屏按行动优先展示：

- “下一步该做什么”主行动卡。
- 当前学习阶段和个人进度。
- 最近一次诊断摘要。
- 一个推荐资源或实操任务。
- 最近反馈和个人学习摘要。

不展示 Agent 运行状态、系统任务、全局学习者数量、全局幻觉率和学习者列表。

### 教师：培训管理台

展示教师有权限范围内的：

- 班级/学习者进度摘要。
- 待关注学习者和停滞任务。
- 知识盲区分布。
- 学习者列表及详情入口。

不默认展示 Agent 基础设施状态；需要运维信息时通过管理员授权入口进入专门页面。

### 管理员：系统总览

保留当前管理员所需的系统指标、Agent 状态、近期任务和资源统计，但将详细运维能力导向 `/ops`、`/multi-agent`、`/metrics` 和 `/monitoring`。

## 4. 学习者引导状态机

引导阶段由持久化业务事实计算，优先使用服务端字段 `onboarding_completed_at` 和 `dashboard_guidance_dismissed_at`。在字段尚未提供时，临时按以下事实判断：

```text
画像不完整
  -> 完善学习者画像
无诊断记录
  -> 开始首次诊断
已有诊断但无资源
  -> 生成首份个性化资源
有资源但未完成学习
  -> 开始自适应导学
已完成一轮学习
  -> 查看反馈并进入下一知识点
```

引导卡提供“继续”“稍后处理”“查看详情”操作；完成或稍后处理状态必须在刷新和换设备后保持一致。引导状态只决定用户体验，不作为权限判断。

## 5. 数据请求与刷新矩阵

| 角色 | 首屏请求 | 默认刷新 |
|---|---|---|
| learner | 当前画像、个人学习摘要、最近资源、当前用户的学习任务 | 不轮询；答题/资源生成/导学结束后局部刷新；回到页面时按需刷新 |
| teacher | 班级摘要、授权范围内学习者分页列表、待处理任务 | 手动刷新为主，必要时使用不少于 60 秒的低频刷新 |
| admin | 系统指标、Agent 状态、任务列表 | 保留 30 秒轮询，仅在管理员 Dashboard 或运维页启用 |
| ops | Agent 状态、任务、运行信息 | 由专门运维页承担高频刷新 |

实施约束：

- 删除 Dashboard 中未使用的 `fetchResources({ page: 1, pageSize: 50 })` 请求。
- 学习者任务必须由当前用户范围的接口返回，不能复用管理员的全局系统任务列表。
- 请求函数按角色分组，不能通过“先请求后隐藏”实现权限控制。
- 可见性刷新需进行角色判断、并发去重和最短刷新间隔控制。
- 单个模块请求失败时只影响该模块，不能阻塞整页；显示可重试的错误状态。
- 个人摘要和班级摘要优先使用聚合接口，避免前端拼接大量明细请求。

## 6. 组件与模块边界

保留现有公共 `Card`、表格、骨架屏和空状态组件，新增页面级模块：

- `LearnerDashboard`：引导卡、个人进度、推荐资源和反馈摘要。
- `TeacherDashboard`：班级概览、风险学习者和学习者列表。
- `AdminDashboard`：系统统计、Agent 状态和近期任务。
- `DashboardDataLoader` 或等价的角色分流逻辑：只负责根据角色调用允许的请求。

不在本次工作中拆分无关页面，也不引入一次性通用抽象。若现有 Dashboard 文件拆分后仍保留纯展示辅助函数，应保持其现有行为。

## 7. 空状态与异常处理

- 无画像：引导至画像完善，不显示“0% 已完成”等误导性指标。
- 无诊断/资源/任务：显示下一步行动，而不是空白列表。
- 数据部分失败：保留可用模块，失败模块显示错误原因和重试按钮。
- 权限不足：隐藏不适用模块；若服务端返回 403，显示无权限状态，不自动重试。
- 聚合接口不可用：允许回退到已有个人/班级接口，但必须记录降级事件，避免静默增加请求量。

## 8. 验收标准

### 功能

- 三种角色登录后显示不同的信息结构。
- 新学习者首屏存在唯一主行动，登录到首次有效学习动作不超过 2 次点击。
- 引导状态覆盖画像、诊断、资源、导学和反馈五个阶段，并可持久化。
- 管理员仍可访问全部运维页面和系统监控数据。

### 性能与请求

- learner 首屏不请求 Agent 状态、系统任务或全局指标。
- 删除未使用资源请求后，学习者首屏请求数相较当前至少减少 40%。
- learner 停留 5 分钟不产生无意义后台轮询。
- 标签页切换不会产生重复并发刷新。

### 安全与权限

- learner 只能请求当前用户个人数据。
- teacher 只能读取授权班级/学习者范围。
- 角色-接口白名单有单元测试覆盖。

### 测试

- 角色渲染和请求数量测试。
- 轮询启停与可见性刷新去重测试。
- 引导状态机各阶段及持久化测试。
- 部分接口失败、403 和空数据测试。
- 至少一条端到端路径覆盖“新学习者登录到完成首轮导学”。

## 9. 分阶段实施计划

### 阶段一：基线与数据边界

记录各角色首屏请求数、响应体积和首屏耗时；确认个人摘要、班级摘要 API；删除未使用资源请求；建立角色-接口白名单。

### 阶段二：角色化 Dashboard

拆分学习者、教师、管理员页面级模块；接入角色数据加载器；将系统监控入口明确指向现有运维页面。

### 阶段三：新手引导状态机

实现五阶段引导卡、持久化完成/稍后处理状态和各类空状态；保证新手首个行动路径不超过两次点击。

### 阶段四：刷新与缓存治理

管理员保留 30 秒轮询；学习者改为事件触发和按需刷新；教师使用手动或低频刷新；加入请求去重、取消过期请求和短时缓存。

### 阶段五：自动化验收与演示数据

补齐单元测试和端到端测试；在演示环境准备三种角色、完整引导阶段和最小可用学习记录，验证请求矩阵、指标展示和角色边界。

## 10. 关键假设与风险

- 假设 `user.role` 在 Dashboard 首次渲染前可用；若存在异步恢复，需要先显示角色恢复骨架屏，不能先按管理员请求。
- 假设现有 API 能按当前用户和教师授权范围过滤；否则必须先补服务端过滤，前端隐藏不能替代权限控制。
- 若新增聚合接口，会增加后端改动，但能显著降低首屏请求数量和前端耦合。
- 不使用真实敏感学习数据作为演示样本；演示数据应为脱敏或合成数据。
