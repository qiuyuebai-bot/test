# 学习工作赛道 - 领域知识个性化生成与多智能体协同决策系统

## 1. Demo 简介

**是什么**：一套面向教育学习场景的 Web 系统，基于多智能体协同的领域知识个性化学习资源生成平台，融合学情分析、知识图谱、幻觉检测与自适应导学能力。

**面向谁**：
- 需要个性化学习资源的学习者
- 需要管理学员画像与培训内容的企业培训/教学机构
- 需要可视化学情数据与教学效果评估的教育工作者

**主要功能**（3 个核心功能）：

**① 多智能体协同决策（核心创新点）**
系统内部分工三类智能体——学情诊断 Agent（分析学习者知识盲区）、领域专家生成 Agent（产出个性化学习资源）、审核裁判 Agent（质量审核与幻觉检测），三者通过"辩论交叉验证"闭环机制相互校验与修正，抑制大模型生成幻觉。前端以三栏式可视化页面呈现 Agent 协同全过程：左侧角色面板、中间动态拓扑、右侧实时日志与纠错记录。

> 📷 **截图位置 1**：多智能体协同可视化页面（三栏布局，展示 Agent 辩论过程与纠错记录）
> 建议截取 `http://localhost:5173/multi-agent` 页面，包含 Agent 动态拓扑图与实时日志面板

**② 学情画像与个性化资源生成**
基于学习者答题记录与行为数据，构建多维学情画像（知识掌握度、学习风格、认知水平），并据此动态生成练习题、讲解材料与学习路径。学情报告页支持雷达图、热力图、趋势曲线与能力雷达可视化。

**③ 领域知识库与幻觉检测**
支持文档上传、智能切片、向量索引（ChromaDB）与语义检索；生成内容自动经过规则 + 嵌入相似度的分级幻觉检测，并提供量化指标监控（幻觉率、匹配准确率、知识覆盖率、智能体成功率）。

**技术栈**：React 18 + TypeScript + Vite + Tailwind CSS + FastAPI + SQLAlchemy + ChromaDB + Redis + Docker

## 2. Demo 创作思路

**灵感来源**：
在教育与培训场景中，大模型生成学习资源存在一个核心矛盾——内容丰富但"不可信"，常出现事实性错误（幻觉）。学员若按错误内容学习，后果比没有资源更严重。我们思考：能否用"多智能体辩论"的机制，让 Agent 之间相互质疑与校验，像同行评审一样把幻觉压制在产出环节？

**想解决的问题**：
- **学习者侧**：通用学习资源"千人一面"，无法匹配个人知识盲区；且 AI 生成内容存在幻觉风险，学习者难以辨别
- **培训机构侧**：学情数据分散在答题记录、行为日志、考核成绩中，缺乏统一画像；高质量个性化资源制作成本高、效率低
- **教学评估侧**：缺乏对生成内容质量的量化监控，"幻觉率""知识覆盖率"等指标无从谈起

**为什么做这个方向**：
- **真实痛点**：AI 生成内容的可信度是教育场景的底线问题，比"生成得多"更重要的是"生成得对"
- **技术判断**：单 Agent 自我校验能力有限，多 Agent 辩论交叉验证是当前工程上可落地的幻觉抑制方案
- **差异化**：市面上学习类产品多为"单点功能"（刷题/讲解/测评），缺少从学情诊断到资源生成再到质量审核的完整闭环
- **可演示性**：多智能体协同过程天然适合可视化，契合揭榜挂帅演示与答辩的展示需求

## 3. Demo 体验地址

**体验方式**：交互式 HTML 资源包（Zip 格式上传到社区）

由于本系统为前后端分离架构（前端 React + 后端 FastAPI + 数据库），完整体验需要后端服务支撑。体验包提供两种方式：

**方式一：一键 Docker 部署（推荐，完整功能体验）**
- 前置要求：已安装 Docker Desktop
- 解压后双击 `docker-start.bat`（Windows）或执行 `./docker-start.sh`（Linux/Mac）
- 脚本自动完成：环境检测 → 配置初始化 → 镜像构建 → 容器启动 → 健康检查 → 浏览器打开
- 访问地址：`http://localhost`
- 默认账户：`admin` / `admin123`

**方式二：前端交互式预览（快速查看界面与交互）**
- 解压后直接用浏览器打开 `dist/index.html`
- 可查看全部 12 个功能页面的 UI 与交互效果（API 数据为前端预置示例数据）

> 如需 AI 生成功能，请在 `.env` 中配置 `OPENAI_API_KEY` 后使用方式一启动。

## 5. 开发心得与经验总结

**关于"用 TRAE 做出来"的真实感受**：

整个项目从 UI 优化到系统重构再到诊断修复，全程使用 TRAE 作为唯一开发工具。几点深刻体会：

1. **意图驱动的开发效率**：TRAE 对"保留业务逻辑、只升级视觉"这类带约束的指令理解准确，在 UI 重构时没有破坏任何原有数据接口，降低了返工成本。

2. **跨阶段上下文一致性**：通过 memory 机制，TRAE 在不同会话间能保持对项目硬约束（如"严禁硬编码""深空蓝主色""8px 间距基准"）的记忆，避免每次重复交代背景。

3. **代码审查闭环**：最后阶段的系统性诊断修复让我印象最深——TRAE 自己产出代码审查报告，识别出 4 个 Critical 安全问题（知识库路由无认证、IDOR 越权、文件上传 OOM、React 渲染副作用），再自己按报告逐项修复并跑通回归。这种"审查 → 修复 → 验证"的闭环，单靠人工审查很难做到这个覆盖度。

4. **工程化而非仅写代码**：TRAE 产出的不只是功能代码，还包括 Docker 多阶段构建、Helm Chart、CI/CD pipeline、Prometheus 监控、审计日志、E2E 测试套件——这些都是"能演示"与"能上线"之间的差距，TRAE 帮忙补齐了这层工程化能力。

**最大的经验教训**：早期 mock 数据埋得越多，后期接入真实 API 的成本越高。如果重来，会在第一天就用 TRAE 先把后端骨架和 API 契约定下来，而不是先堆前端 mock。
